# OpenAutoPath 服务器模式构建方案

**状态**　首版已在 `feature/cam-server` 分支实现。本文记录目录和依赖设计，实际构建、启动、HTTP 接口及原生集成测试见[服务器使用说明](../server/README.md)。

**首版目标**　用户通过一个浏览器地址上传 STEP，查看识别出的孔，选择孔和刀具，生成并预览刀路，最后下载 NC 文件。

## 1. 仓库与进程边界

采用**同一 Git 仓库、独立子项目**。桌面程序和服务器 worker 在同一源码版本上链接 C++ 领域库，使加工参数、刀路验证和后处理的变更可以一次提交、两端验证。Go 服务和网页各自管理依赖、构建和测试。将来若服务器需要独立发版，且能直接使用有版本号的 worker 发布包，再评估分仓。[现有模块及依赖说明](../ARCHITECTURE.md)

```text
桌面用户 → Qt 桌面应用 ────────────────────────→ C++ 领域库
浏览器   → React / Three.js → Go HTTP 服务 → C++ worker → 同一组领域库
```

Qt 端继续负责窗口、面板、项目交互和桌面渲染。服务器 worker 通过领域模块的公开接口执行计算。比如 AABB 边界面判断归分析模块，孔加工规则归相应的加工模块，浏览器中的特征树和属性面板归 Web 前端。若某条加工规则目前位于桌面工作流中，待第二个调用方实际用到时，把该规则提取到对应领域模块。[几何分析示例](../src/analysis/detail/AabbBoundaryFace.cpp) · [Qt 工作流面板](../src/app/ui/panels/CamWorkflowPanel.cpp)

## 2. 目录组织

```text
OpenAutoPath/
├── src/
│   ├── analysis/                 已有 · STEP 读取与几何分析
│   ├── recognition/              已有 · 加工特征识别
│   ├── tooling/                   已有 · 刀库及加工参数适配
│   ├── toolpath/                  已有 · 刀路、验证与后处理
│   ├── manufacturing/             已有 · 工序、加工项目和在制毛坯
│   ├── app/                       已有 · Qt 桌面应用
│   └── worker/                    新增 · C++ 命令行入口和协议适配
├── server/                        新增 · Go module
│   ├── go.mod
│   ├── cmd/oap-server/            启动入口、配置和依赖装配
│   └── internal/
│       ├── api/                   HTTP 接口、项目访问检查
│       ├── jobs/                  队列、状态、取消、并发上限
│       ├── worker/                启动 C++ 进程、接收事件和退出状态
│       └── storage/               模型版本、任务记录、结果文件
├── web/                           新增 · React、TypeScript、Vite
│   ├── package.json
│   └── src/
│       ├── features/              项目、特征树、刀具和工序面板
│       ├── viewport/              Three.js 选面、高亮和刀路回放
│       └── api/                   Go HTTP 接口客户端
├── contracts/                     新增 · 跨语言接口定义和样例
│   ├── http/                      浏览器与 Go 的请求和响应
│   └── worker/                    Go 与 C++ 的请求、事件和结果清单
└── cmake/                         已有 · 登记 worker 源文件与模块依赖
```

`src/worker/` 和 `server/internal/worker/` 分别对应计算进程和进程调用方。前者可以用一个任务文件在命令行单独复现计算，后者将退出码、诊断信息和输出文件转换为用户能查询的任务状态。

## 3. 一次加工任务如何流转

1. **上传与分析**　Go 保存 STEP，为这次上传分配模型版本。网页提交分析请求后立即取得任务 ID。Go 按并发上限启动 worker，每次执行使用独立工作目录。worker 读取 STEP，调用分析和识别模块，输出孔列表及诊断信息。
2. **显示与选择**　worker 输出预览网格，并记录网格三角形与 CAD 面、加工特征的对应关系。网页点选孔壁后可高亮整个特征。生成刀路的请求携带模型版本、特征 ID、刀具与加工参数，worker 在该版本内解析这些引用。
3. **生成与导出**　Go 保存此次计算的输入快照并创建新任务。worker 复用孔加工、程序验证和 NC 导出模块，输出刀路预览、验证报告和结果清单。Go 在确认成功退出且所需产物齐全后发布结果。网页按任务 ID 查询状态，刷新或重新打开后可继续查看和下载。

首版用 HTTP 轮询更新网页状态。Go 与 worker 之间采用带协议版本的 JSON 请求文件、标准输出上的逐行 JSON 事件，以及结果清单。普通日志写入标准错误，大体积网格和刀路使用独立文件，清单记录其相对路径。按项目检查上传与结果访问权限，由 Go 分配实际存储路径。取消或失败时仅发布任务终态和诊断，重试使用新的执行目录。

## 4. 构建与交付

| 产物 | 构建入口 | 交付方式 |
|---|---|---|
| Qt 桌面应用 | 现有桌面 CMake preset | 沿用桌面发布包 |
| `oap-worker` | 根 CMake 拟新增独立可执行目标，定义在 `if(OAP_BUILD_GUI)` 之外 | 随服务器包提供对应平台的二进制和所需原生运行库 |
| `oap-server` | 在 `server/` 用 Go 构建 `./cmd/oap-server` | 启动时指定 worker、静态资源和可写数据目录 |
| Web 工作台 | 在 `web/` 用 Vite 构建 | 将 `dist/` 随包交给 Go 托管，通过同一域名访问页面及 `/api` |

新增 worker 时，按仓库惯例登记源文件和直接依赖。Windows 上可从现有 `windows-core` preset 验证无界面构建。刀库和制造模块当前链接 `Qt6::Core`，服务器包应包含实际链接所需的 Qt Core、OCCT 等运行库。Windows 的 core preset 已关闭桌面运行库部署，打包验收应在独立目录启动 worker，确认它能完成样例任务。[CMake 目标定义](../CMakeLists.txt) · [构建预设](../CMakePresets.json) · [现有构建说明](../BUILDING.md)

首版部署在单台服务器上，由 Go 托管页面、管理任务和拉起 worker。静态页面与可执行文件属于发布包，上传的模型、任务记录和计算结果放在包外的可写数据目录，以便升级和备份。

## 5. 实施顺序与验收

| 阶段 | 实现范围 | 验收标准 |
|---|---|---|
| 1 · 无界面分析 | 增加 worker 和首个协议样例，打通 STEP → 孔列表 | 关闭 GUI 构建后，在命令行分析同一测试模型，孔数量及几何参数与桌面版一致 |
| 2 · 浏览器提交任务 | 增加 Go 服务和上传、状态、结果页面 | 上传后获得任务 ID，刷新页面可取回结果；损坏的 STEP 返回失败原因，服务能继续处理下一任务 |
| 3 · 三维选择 | 导出带面映射的网格，实现列表与视口联动 | 点孔壁能选中对应列表项，点击列表项能高亮对应几何；模型版本变更后能识别失效选择 |
| 4 · 孔加工闭环 | 接入刀具选择、刀路生成、验证、预览与 NC 下载 | 同一模型、装夹、工序和刀具参数下，与桌面版核对工序顺序、刀路和 NC 加工指令；浏览器可下载该次任务的结果 |

首版以孔加工闭环作为服务器交付点。后续接入口袋、轮廓和仿真时，继续由 C++ 领域模块提供计算能力，在 worker 协议、Go 接口和网页中增加对应操作。

## 6. 加工项目与刀库实施进度

Web 工作台已接入桌面版的 `.oapjob` 和 `.oaptl` 读写模块。Go 管理会话、文件版本、历史模型和任务，`src/worker/` 复用 C++ 的项目、刀库、规划和 IPW 模块，React 与 Three.js 提供编辑和预览。工序引用保存时的刀具快照。切换活动刀库会影响后续规划，历史项目可按原参数重新计算。

验收覆盖 STEP 测试件的孔、槽腔、外轮廓和雕刻工序、混合工序余料、参考 NC、文档往返和会话隔离。外部毛坯和碰撞模型的重新绑定、完整项目的分装夹 NC 程序包仍属于后续范围。构建和操作见[服务端说明](../server/README.md)。
